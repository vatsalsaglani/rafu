01Honest assessment

Rafu has a good palette and a sound architecture. It does not yet look like one designed application. It looks like many careful features, each with its own controls.

Keep these

  • The Indigo palette. It is dark, cool and quiet. Code and Markdown read well on it (editor.jpg, markdown-split.jpg).
  • The Markdown preview typography: a clear H1, good line length, real bullets.
  • The side-by-side diff: calm red and green rows with word-level marks (git-diff.jpg).
  • The terminal pane header: name, state, and three familiar icons (pencil, play, close) in terminal-editor.jpg.
  • Honest privacy text: "Rafu never starts one on its own", "Keys stay in this Mac's Keychain".
  • The command palette: one field, prefixes, keyboard hints.
  • Empty states with a symbol, a title and one line of text.
  • The stash menu: the destructive item is last, after a separator (menu-git-stash.jpg).

Fix these

  • Gold is everywhere. A gold frame surrounds the editor in every main image. Gold also marks ellipsis icons, sync icons, text buttons and branch names. Gold no longer means "focus" or "important".
  • Too many text buttons. The Canvas has 6 toolbar buttons, 5 zoom buttons and a "Focus" button on every card. The Canvas list has 10 bordered buttons for 5 rows.
  • The right panel breaks at its width. Labels wrap inside words: "Worktree s", "Workflo ws", "Ca se", "Who le Wor d". One panel is clipped.
  • The Canvas is a set of floating panels. Cards look equal, overlap with no depth cue, and carry headers, footers, link circles and help text at the same time.
  • Settings is a tab with its own sidebar. With Files and Source Control open, the window shows three sidebars.
  • Words come from the code, not from the user: "Parked", "Leave Content", "Session bridge stopped", "Bounded lifecycle events", "Verb version", "1 panes".

02Visual direction: "One Gold Thread"

Rafu means darning: a careful repair with one thread. The interface is the cloth. It is quiet, even and neutral. Gold is the thread. It appears only where something is joined, focused or alive.

The look

  • Cloth surfaces. Three tonal steps of indigo (backing, deck, raised). Hairlines separate them. No glass, no gradients, no texture.
  • One thread of gold. Gold marks keyboard focus inside content, the current selection, a live agent link and the one primary button in a view. Nothing else is gold.
  • Stitches for relationships. A plain relationship is a short dashed line, like a running stitch. A live agent link is a solid gold thread. The metaphor is functional, not decorative.
  • Literary text, technical data. New York for Markdown and note prose. SF Pro for interface text. SF Mono for code, paths, hashes and counts.
  • Depth only where space is real. The workbench stays flat. The Canvas is a spatial surface, so its nodes get one soft shadow that shows stack order.

The feel

  • Calm at rest. Controls that are not needed now are hidden until hover, selection or keyboard focus. They are always in a menu.
  • Precise under the pointer. Drag, resize and connect follow the pointer 1:1. Snaps are instant. Feedback comes from guides, not from bounce.
  • Immediate under the keyboard. Typing, cursor movement, terminal input, tab changes and list navigation have no animation.
  • Honest about state. Each state has a word and a shape, and then a colour. A paused link says "Paused".
  • Native first. Standard Settings window, standard menus, standard sheets, standard focus rings in the theme colour.

07Canvas interaction specification

One rule organises the Canvas: the header moves the card; the body uses the content. Everything else follows from it. This section says "node" for the model and "card" for the user-visible word.

7.1 Node anatomy

  1. 1Header = move handle. 32 pt. Drag anywhere in it to move. Glyph and title in constant screen size.
  2. 2State word + shape. "Running", "Not running", "Exited (1)". The dot is secondary.
  3. 3Content-focus control. Appears only while the body has keyboard focus. Click it, press ⌃⇥, or click the board to return.
  4. 4Hover actions. Zoom to Card, primary action (Open in Editor / Open App), "⋯" menu. Hidden at rest, visible on hover, selection and keyboard focus.
  5. 5Port under the pointer. 8 pt → 12 pt, gold. Drag to connect. The gold line is a live message link.
  6. 6Resize. 8 pt hit zones on all edges; corner handles show on selection.
  7. 7Content focus ring. 1.5 pt gold inner stroke and an 8% gold header tint. One node at a time.
  8. 8Note progress. Task count "3/5" stays readable when zoomed out.
  9. 9Tasks toggle in Read mode. The click edits the Markdown source and is undoable.
  10. 10Code block. SF Mono on the deck colour, copy button on hover, horizontal scroll inside.

7.7 Terminal focus

  • First click enters. A mouse-down in a terminal body makes the terminal the first responder in the same event. The user can type at once. No second click.
  • Visible state. Gold inner stroke, header tint, block cursor solid (not blinking when Reduce Motion is on), "Return to Board ⌃⇥" in the header.
  • Keys go to the CLI. All keys without ⌘ go to the PTY: esc, ⌃C, ⌃D, ⌃R, Tab, arrows, ⌥ as Meta when the user enabled it. ⌘ shortcuts go to the menu bar, except ⌘C/⌘V/⌘K (copy, paste, clear) which the terminal handles. ⌃⇥ is the only extra key Rafu takes. Needs test with Claude Code, Codex and vim.
  • Native colours. The terminal body uses the terminal palette and ANSI colours unchanged. Node chrome stays neutral around it. Rafu does not tint output.
  • Scroll. With content focus, scroll goes to the terminal scrollback. Without focus, scroll pans the board. A second finger pause (no movement for 300 ms) is not needed; focus decides.
  • Selection and copy. Text selection inside the terminal with drag; ⌘C copies. Drag inside the body never moves the node.
  • Resize. During a resize drag the content scales visually; the PTY gets one size change on mouse-up. This avoids reflow storms in the CLI.
  • Leaving. Click on the board, click on another node, ⌃⇥, or the header button. Focus leaves; selection stays on the terminal.

Optional haptics

Verified on Apple's documentation (18 Oct 2026):

  • AppKit NSHapticFeedbackManager gives access to haptic feedback "on a system with a Force Touch trackpad". Patterns: .generic, .alignment, .levelChange. Performance times: .default (next screen update), .now, .drawCompleted.
  • The default performer is chosen "based on the current input device, accessibility settings, and user preferences". A mouse or an external trackpad without Force Touch gives no feedback.
  • Apple says haptics are "intended to be provided in response to a user action" and "Do not use it to provide feedback for events that are not user initiated." So no haptic for incoming agent messages.
  • SwiftUI sensoryFeedback (macOS 14+): .alignment plays on iOS and macOS; .levelChange plays on macOS only; .success, .error, .impact, .selection play only on iOS/watchOS. So no success or failure haptic on the Mac.
